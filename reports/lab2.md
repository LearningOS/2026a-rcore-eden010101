# Lab2 地址空间实验报告

## 一、功能总结

这次实验主要补完了 `trace`、`mmap` 和 `munmap`。`trace` 需要根据用户虚拟地址查页表，并检查 PTE 的有效位和读写权限；`mmap` 负责检查地址和权限是否合法，再给当前进程建立新的页映射；`munmap` 则负责检查目标页是否已经映射，并解除映射、回收对应的物理页。最后 Chapter 4 的测试结果为 16/16。

## 二、问答作业

### 1. SV39 页表项由哪些部分组成？各标志位有什么作用？

SV39 的 PTE 是 64 位的，里面最重要的是 PPN 和一些权限位。

PPN 用来记录物理页号。几个比较重要的标志位是：

- `V`：这个 PTE 是否有效；
- `R`：是否可读；
- `W`：是否可写；
- `X`：是否可执行；
- `U`：用户态能不能访问；
- `G`：是不是全局映射；
- `A`：这个页有没有被访问过；
- `D`：这个页有没有被写过；
- `RSW`：留给操作系统软件自己使用。

这次实验里我对 `V` 和 `U` 感受比较明显。`trace` 里不能只找到 PTE 就算成功，还要看 `V`，访问用户地址还得检查 `U`。另外 `mmap` 的 `port` 和 `MapPermission` 的位并不是直接对应的，所以中间还要做一次转换。

### 2. 缺页

#### 2.1 哪些异常可能和缺页有关？

主要有三种：

- Instruction Page Fault
- Load Page Fault
- Store/AMO Page Fault

也就是取指、读内存、写内存时，如果对应虚拟页没有合法映射或者权限不对，就可能产生 Page Fault。

#### 2.2 缺页时几个重要寄存器保存什么？

我理解最关键的是：

- `scause`：告诉内核这次 Trap 是什么原因；
- `stval`：一般保存发生问题的虚拟地址；
- `sepc`：保存发生异常时的指令地址；
- `sstatus`：保存 Trap 前后相关的状态；
- `satp`：表示当前使用的是哪张页表。

其中处理缺页时最直接的是 `scause` 和 `stval`。先通过 `scause` 判断是哪种 Page Fault，再通过 `stval` 找到具体哪个虚拟地址出了问题。

#### 2.3 Lazy 分配有什么好处？

Lazy 的核心就是“先不分配，真正访问时再分配”。

这样做的好处是不会一申请内存就马上占用大量物理页。很多程序申请的空间不一定真的全部用到，如果一开始全部分配会浪费内存，也会增加建立页表的开销。

所以 Lazy 更适合这种“申请得多，实际用得少”的情况。

#### 2.4 10 GiB 连续内存大概需要多少页表空间？

页大小是 4 KiB。

10 GiB / 4 KiB 大约是 262 万个页。

一个 PTE 是 8 字节，所以只算最末级页表：

262 万 × 8 B，大约就是 20 MiB。

再加上上层页表，也还是几十 MiB 这个量级。

这个计算让我比较直观地感觉到：就算物理页还没真的全部分配，页表本身也不是完全没有成本。

#### 2.5 Lazy 大概怎么实现？

我的理解是：申请内存的时候先只记录“这段虚拟地址是合法的”，但先不真正分配物理页。

程序第一次访问时，因为 PTE 还没有有效映射，所以触发 Page Fault。

内核接到异常以后：

1. 从 `stval` 找到出问题的虚拟地址；
2. 看它是不是属于一个合法的 Lazy 区域；
3. 如果合法，就分配一个物理页；
4. 建立 VPN 到 PPN 的映射；
5. 设置好权限；
6. 返回用户态，让原来的指令重新执行。

如果这个地址本来就不属于合法区域，那就是非法访问，不能给它补页。

#### 2.6 Swap 出去以后，PTE 怎么表示？

如果一个页已经被换到磁盘上了，就不能继续把它当成一个正常的内存映射。

一种做法是把 PTE 的 `V` 位清掉，让 CPU 下次访问时产生 Page Fault。

操作系统还得另外保存“这个页在交换区的什么位置”。之后缺页处理时再把它读回内存，重新建立 PTE。

### 3. 单页表和双页表

#### 3.1 单页表什么时候需要切换页表？

如果用户空间和内核空间都放在同一张页表里，那么用户态进入内核态时通常不用换页表。

真正需要换页表的地方主要是进程切换。例如从进程 A 切到进程 B，就要让 `satp` 指向 B 的页表。

#### 3.2 单页表怎么防止用户直接访问内核？

靠 PTE 的 `U` 位。

用户页设置 `U=1`，内核页设置 `U=0`。

这样即使用户空间和内核空间同时出现在一张页表里，U-mode 也不能直接访问 `U=0` 的内核页面。

#### 3.3 单页表有什么好处？

最大的好处就是用户态进入内核态的时候不用来回切页表。

这样可以少改 `satp`，也能减少一些 TLB 刷新的开销，Trap 的流程也会简单一些。

缺点就是用户页表里也会有内核映射，所以权限隔离一定要做好。

#### 3.4 双页表什么时候需要换页表？如果自己实现单页表会怎么做？

双页表下，用户态和内核态使用不同页表。

所以用户态发生 Trap 进入内核时要切到内核页表，返回用户态的时候再切回当前进程的用户页表。

如果让我实现单页表，我会让同一个进程从用户态进入内核态时继续使用原来的页表，只在进程切换时修改 `satp`。这样逻辑会更直接一些。

## 三、实验过程中遇到的问题

这次实验前面最容易混的是 VA、VPN、PTE、PPN 这几个东西。

一开始我不太理解为什么一个 VPN 就能找到 PTE，后面才理清楚：VPN 不是 PTE，它只是查页表时用的索引。大致关系是：

```text
VA
↓ floor()
VPN
↓ 查页表
PTE
↓
PPN
```

做 `mmap` 的时候，我一开始用的是：

```rust
memory_set.translate(vpn).is_some()
```

我当时以为只要 `Some` 就说明这个页还在使用。

但是做到最后一个测试时发现不对。`munmap` 之后，PTE 的槽位可能还存在，只是已经被清空，`V=0`。所以这时候 `translate(vpn)` 还是可能得到 `Some(pte)`，但这个 PTE 已经不是有效映射了。

最后改成检查：

```rust
if let Some(pte) = memory_set.translate(vpn) {
    if pte.is_valid() {
        return false;
    }
}
```

之后最后一个测试才通过。

`munmap` 这里我一开始也以为只要把页表项删掉就行。后来看到 `unmap_one()` 才发现，Framed 页还要把 `data_frames` 里的 `FrameTracker` 删除。`FrameTracker` 被 drop 以后才会真正调用物理页回收，所以解除映射其实包含两件事：

1. 页表里不再有 VPN 到 PPN 的有效映射；
2. 对应物理页也要被回收。

另外这次还碰到了不少 Rust 本身的问题，比如 `VPNRange` 没有导出、`munmap_current` 没有 import、项目开启了 `deny(missing_docs)`，新增的 `pub fn` 必须写文档注释。这些问题虽然不属于操作系统原理，但确实花了不少时间排查。
