# Lab4（ch6/ch7）实验报告

## 实现的功能

这章主要做硬链接相关的三个系统调用。linkat 在根目录里追加一个目录项，名字是新的，inode 编号指向已有文件。unlinkat 把对应目录项清空（名字置空），再扫一遍根目录数这个 inode 还剩几个有效名字；剩 0 就清掉数据块。fstat 从 fd 表拿到打开的文件，读出事先在 open 时记下来的 inode 编号，再遍历根目录算 nlink，填进用户的 Stat。easy-fs 的 DiskInode 本身没有链接计数字段，所以 nlink 都是现场数的。本地 `make test CHAPTER=6` 测例 31/31 过了。

## 问答题（ch6）

**在我们的 easy-fs 中，root inode 起着什么作用？如果 root inode 中的内容损坏了，会发生什么？**

easy-fs 只有一个扁平的根目录，所有文件名到 inode 的映射都记在 root inode 对应的那块目录数据里。打开、创建、硬链接、unlink、按名字找文件，全都得先从 root inode 读目录项。它相当于整棵「目录树」的唯一入口（虽然这里其实没有子目录）。

如果 root inode 坏了，比如目录项内容乱掉、size 错了，或者它自己的数据块丢了，那名字就对不上 inode 了：按名字找不到文件，link/unlink/fstat 的遍历也会错，新创建也可能写到错误位置。inode 区和数据区里的内容可能还在磁盘上，但没有正确的目录项就访问不到，等于文件系统从用户视角废了。根 inode 本身如果在位图或 inode 区被破坏，连「打开根目录」这一步都会出问题。

## 问答题（ch7）

**1. 举出使用 pipe 的一个实际应用的例子。**

平时在终端里最常见的就是把一个命令的输出接到另一个命令的输入，比如统计文件行数：

```bash
cat notes.txt | wc -l
```

`cat` 往管道里写文件内容，`wc` 从管道另一端读，数有多少行。中间不用临时文件，两个进程靠管道传递字节流。

**2. 如果需要在多个进程间互相通信，则需要为每一对进程建立一个管道，非常繁琐，请设计一个更易用的多进程通信机制。**

一对进程一条管道的话，n 个进程两两通信就是很多条管道，创建和管理都烦。可以做成「带名字的邮箱 / 消息队列」：内核维护一张表，每条消息有目标标识（进程 pid，或者一个大家约定好的 channel 名）。发送方调用 `send(dest, buf)`，接收方 `recv(buf)` 或按 channel 阻塞等待。这样进程不用两两建 pipe，也不用自己保管一大堆 fd，只要知道对方的名字或 id。短消息、控制信息这种场景比纯字节流管道好用；如果还要传大量数据，可以再在上面叠一块共享内存，消息队列只负责通知「数据准备好了」。
